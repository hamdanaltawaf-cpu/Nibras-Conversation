# YemReact — نطاق الـMVP النهائي وتوجيهات التنفيذ

**إلى:** فريق/مطوّر التنفيذ
**من:** مالك المشروع
**الموضوع:** نطاق الـMVP المعتمد، القرارات المعمارية النهائية، ومسؤوليات التنفيذ

هذا المستند هو **المرجع الوحيد** لنطاق الـMVP اعتبارًا من تاريخه. أي نقاش سابق حول الميزات أو الأولويات يُعتبر منتهيًا وتم حسمه بما هو مذكور هنا. لا اجتهاد فردي في أي بند مذكور كـ"معتمد" — الاجتهاد مسموح فقط داخل التفاصيل التقنية للتنفيذ، لا في نطاق الميزات نفسه.

**الفلسفة الحاكمة لأي قرار لاحق:**
> YemReact يساعد المستخدم يلاقي الرياكشن اليمني المناسب للموقف بأسرع طريقة، ويعطيه إياه جاهزًا للاستخدام.
> أي ميزة لا تخدم مباشرة: **الاكتشاف + الوصول + الحفظ + الأخذ + المشاركة + بناء المكتبة** — تُرفض بشكل افتراضي، ولا تُبنى إلا بموافقة كتابية صريحة مني.

## 1. نطاق الـMVP المعتمد (إلزامي بالكامل)

كل بند أدناه **جزء من الالتزام**، لا اقتراح. التسلسل بالترتيب يعكس ترتيب البناء الفعلي المطلوب — لا يُبنى بند من مجموعة لاحقة قبل اكتمال المجموعة التي تسبقه.

### أ — الأساس التقني والمكتبة
1. Next.js + PostgreSQL + Routing حقيقي (رابط مستقل لكل Reaction).
2. مكتبة حقيقية (لا بيانات وهمية) — البحث والتصنيفات والوسوم تعمل على بيانات فعلية فقط.
3. حالات فارغة (Empty States) مصمَّمة بعناية لكل من: نتيجة بحث فارغة، تصنيف فارغ، مكتبة في بداياتها.

### ب — أدوات الإدارة وخط الفيديو
4. لوحة إدارة محتوى موسّعة: تصنيفات (أسماء/وصف/ترتيب)، بيانات كل Reaction بالكامل (عنوان/وصف/Situation/Caption/Tags/Thumbnail/الفيديو)، حالة النشر، الأرشفة، مراجعة بيانات المساهمات قبل النشر.
   **حد صريح:** لوحة الإدارة لا تمنح أي صلاحية لتعديل Brand v1.0 (الشعار، الألوان، الخطوط، القواعد البصرية). هذا خارج نطاق أي واجهة إدارية نهائيًا.
5. Video Validation عند الرفع — يشمل إلزاميًا التحقق من مدة اللقطة (2–8 ثوانٍ تقريبًا، حسب دليل الإنتاج المعتمد)، لا فحص الحجم/الصيغة فقط.
6. Smart Video Optimization: نسخة أصلية (Original Master) تُحفظ للمنشور فقط، ونسخة ويب محسّنة هي المعروضة للمستخدم. لا تفاصيل تقنية (Codec/Bitrate/Resolution) تظهر للمسؤول أو المستخدم.
7. Watermark تلقائي يُدمج ضمن خطوة المعالجة نفسها — ليس خطوة منفصلة.
8. Duplicate Detection عبر مطابقة Hash للملف عند الرفع. **نطاق محدد:** كشف الملف المطابق حرفيًا فقط في هذي المرحلة — لا كشف تشابه بصري/إعادة ترميز، هذا خارج MVP.

### ج — الضيف، المزامنة، والمساهمات
9. استخدام كامل بلا حساب (Guest) — تصفح/بحث/حفظ.
10. Save يعمل للضيف بلا أي التزام تسجيل.
11. Google Sign-In **اختياري فقط**، وظيفته الوحيدة مزامنة المحفوظات وربط حالة المساهمات. لا بريد/كلمة مرور، لا حساب تقليدي، لا Profile اجتماعي بأي شكل.
12. نموذج مساهمة مستخدمين: فيديو + وصف اختياري + تصنيف مقترح.
13. مسار مراجعة صريح: **Pending → Reviewing → Approved / Rejected**، مع تسجيل سبب الرفض. لا نشر تلقائي تحت أي ظرف.
14. صفحات قانونية أساسية (شروط استخدام + خصوصية) وإقرار ملكية بسيط عند كل مساهمة.
15. Rate Limiting على مسار الإرسال تحديدًا (منع السبام/الإساءة).

### د — طبقة النمو
16. تحميل/"خذها" — تجربة مكتملة، لا حالة تجريبية.
17. مشاركة حقيقية (Web Share API + نسخ رابط احتياطي).
18. أحداث Analytics داخلية حقيقية: View / Save / Download / Share — **لأغراض داخلية فقط**، لا تُعرض كأرقام عامة للمستخدم بأي صياغة ("عدد المشاهدات"، "الأكثر إعجابًا"، إلخ ممنوعة من واجهة المستخدم نهائيًا).
19. SEO + Open Graph لكل رابط Reaction (معاينة غنية عند المشاركة بفيسبوك/واتساب).

## 2. مؤجّل بعد MVP (غير مطلوب الآن، لا يُبنى قبل إذن صريح)

Collections · PWA · اقتراحات AI للمسؤول (Category/Tags/Caption) · Duplicate Detection بصري/متقدم · تحليلات متقدمة · برنامج "مساهم موثوق" · بحث دلالي (Semantic Search).

هذي البنود **لا تُفتح للنقاش أثناء بناء الـMVP**. أي وقت يُصرف عليها الآن هو وقت مسروق من نطاق القسم 1.

## 3. مستبعد نهائيًا من فلسفة المنتج (ليس تأجيلًا)

اللايكات · التعليقات العامة · المتابعين/Followers · رسائل بين المستخدمين · Leaderboard للمساهمين · نظام نقاط/منافسة بأي شكل · أي "شعبية" مبنية على اللايكات · Trending كواجهة أساسية · أي عداد "الأكثر إعجابًا" ظاهر للمستخدم · Feed لا نهائي بأسلوب TikTok · إشعارات اجتماعية ("فلان أعجب بـ...").

**هذي القائمة ليست Backlog.** لا تُقترح هذي الميزات لاحقًا كـ"تحسين"، ولا تُبنى نسخة مخفّفة منها بذريعة "بسيطة فقط". أي طلب لإضافة نسخة من هذي القائمة يحتاج نقاشًا صريحًا معي يبدأ من سؤال واحد: هل هذا يخدم الفلسفة الحاكمة أعلاه؟ إذا كان الجواب غير واضح فورًا، الجواب لا.

بديل الاكتشاف المعتمد بدل Trending: **"مختار الأسبوع"** (انتقاء يدوي من المسؤول) + **"جديد المكتبة"**.

## 4. القرارات المعمارية النهائية (غير قابلة لإعادة النقاش بدون مبرر مكتوب)

| الطبقة | القرار |
|---|---|
| Frontend + API | Next.js |
| قاعدة البيانات | PostgreSQL مُدارة (Neon) |
| ORM | Prisma |
| تخزين الفيديو | Cloudflare R2 |
| معالجة/تحسين الفيديو | خدمة مُدارة (Cloudflare Stream أو معادل) — **لا** محرك معالجة مبني ذاتيًا بالخادم |
| الاستضافة | Vercel |
| المصادقة | Google Sign-In فقط، اختياري |

أي تغيير على هذي الطبقات يتطلب تبريرًا مكتوبًا (السبب + الكلفة + المخاطرة) **قبل** التنفيذ، لا بعده.

## 5. مسؤوليات التنفيذ — قواعد ثابتة

1. أي ميزة غير مذكورة صراحة ضمن القسم 1 تُعامل كأنها خارج النطاق، بلا استثناء، حتى لو بدت "بسيطة" أو "سريعة التنفيذ".
2. أي قرار تقني غير محسوم في هذا المستند يُرفَع لي كتابيًا **قبل** البناء عليه — لا يُتّخذ قرار منفرد بشأنه ثم يُبلَّغ لاحقًا.
3. الانتقال من مجموعة (أ/ب/ج/د) للتي تليها لا يبدأ إلا بعد اكتمال واستقرار المجموعة السابقة.
4. Brand v1.0 (الشعار، الألوان، الخطوط، القُصاصة، الواترمارك) مرجع مقفل بالكامل. أي حاجة لعنصر بصري غير موجود فيه تُصمَّم بمبادئه، ولا تُفتح كقرار هوية جديد.
5. أي شك في انتماء ميزة لقائمة الاستبعاد (القسم 3) يُحسم لصالح الاستبعاد افتراضيًا، لا لصالح البناء.

## 6. ثلاث نقاط معلّقة — بانتظار القرار النهائي، لا تُنفَّذ الآن

هذي النقاط الوحيدة غير المقفلة بهذا المستند. لا تُبنى ولا يُفترض فيها اتجاه معيّن حتى يصلكم تأكيد كتابي مني تحديدًا.

**النقطة 1 — تسلسل خط الفيديو الداخلي**
هل يراجع المسؤول الفيديو **الخام** فور وصول المساهمة، أو **بعد** المعالجة والتحسين التلقائي؟ التوصية المطروحة: Validate → Optimize → عرض على المسؤول → Approve → Publish. بانتظار تأكيدي على هذا الترتيب تحديدًا قبل ربط أي خطوتين ببعض بالكود.

**النقطة 2 — نطاق الصفحات القانونية عند الإطلاق**
هل تكفي صفحة شروط/خصوصية أساسية + إقرار ملكية بسيط لبدء استقبال المساهمات العامة، أو نحتاج مراجعة قانونية فعلية قبل فتح الاستقبال على نطاق واسع؟ هذا قرار يتحمّل مسؤوليته مالك المشروع فقط، لا الفريق التقني.

**النقطة 3 — مدة الاحتفاظ بالـOriginal Master للمرفوض**
هل تُحذف النسخة الأصلية للمساهمات المرفوضة فورًا، أو تُحفظ لنافذة زمنية محددة (30 يومًا مثلًا) قبل الحذف؟

**لا يبدأ أي عمل يفترض إجابة لأي من النقاط الثلاث أعلاه قبل تأكيدها كتابيًا.**
